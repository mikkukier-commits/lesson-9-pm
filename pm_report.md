# PM Decision Report: MLflow + Prometheus

## 1. Бізнес-контекст ML-задачі

У цьому експерименті модель класифікує квітки ірису на три класи: `setosa`, `versicolor` і `virginica`. Для прогнозу використовуються чотири ознаки: довжина та ширина чашолистка і пелюстки. Датасет містить 150 квіток; дані розділено на train/test у співвідношенні 70/30, із `stratify` та `split_random_state = 7`.

У практичному продукті такий класифікатор міг би підтримувати автоматичне визначення виду ірису за вимірюваннями. Користувачем результату може бути людина або інша система, яка отримує прогноз. Це демонстраційна задача, тому реальний бізнес-користувач і наслідки помилок у наданих даних не визначені.

Для оцінювання використано дві метрики:
- **Accuracy** — частка правильних класифікацій на тестовій вибірці; більше значення краще.
- **Log loss (`loss`)** — штрафує за впевнені неправильні прогнози; менше значення краще.

Для цього експерименту accuracy показує загальну частку правильних прогнозів, а log loss додає інформацію про якість і впевненість прогнозованих імовірностей. Оскільки бізнес-вартість помилок і вимоги до кожного класу не задані, не можна стверджувати, що accuracy сама по собі є достатньою бізнес-метрикою. Для реального використання варто також перевірити confusion matrix, precision/recall по кожному класу та прийнятні пороги якості.

## 2. Аналіз runs у MLflow

У наданих даних є п'ять runs експерименту `iris-classification`. Числові run ID не наведені у вхідній таблиці, тому їх не можна достовірно заповнити. Перед передачею кандидата команді потрібно скопіювати фактичний `run_id` з MLflow UI.

| Run name | Що змінено / модель | Основні параметри | Accuracy | Loss | Artifact є? | Коментар |
|---|---|---|---:|---:|---|---|
| `logreg-strong-reg` | Logistic regression із сильнішою регуляризацією | `C=0.01`, `max_iter=500` | 0.844 | 0.686 | Ні | Найнижча якість серед логістичних моделей за обома наведеними метриками. |
| `decision-stump` | Decision tree з одним рівнем | `max_depth=1`, `random_state=42` | 0.667 | 0.462 | Ні | Найнижча accuracy; модель, імовірно, надто проста для цієї задачі. |
| `logreg-baseline` | Базова logistic regression | `C=1.0`, `max_iter=500` | 0.933 | 0.191 | Ні | Хороший baseline для порівняння з іншими моделями. |
| `rf-small` | Невеликий random forest | `n_estimators=10`, `max_depth=2`, `random_state=42` | 0.933 | 0.228 | Ні | Така сама accuracy, як у baseline, але вищий loss. |

### Відтворюваність і audit trail

Для кожного run наведено назву, тип моделі, параметри та метрики. Це дозволяє зрозуміти основні відмінності між експериментами. Однак у наданій таблиці немає фактичних `run_id`, версії коду, версії датасету або посилання на Git commit. Без цих даних відтворюваність підтверджена лише частково.

Artifact збережено лише для `rf-depth3`. У його папці є `MLmodel`, `model.skops`, `conda.yaml`, `requirements.txt` та `input_example.json`. Для інших runs model artifacts відсутні, тому їх не можна вважати готовими до передачі чи відтворення на основі артефакту.

## 3. Кандидат на staging / production

**Попередній кандидат — `rf-depth3`.**

Причини:
1. Має найвищу accuracy: **0.956**.
2. Має найнижчий loss: **0.141**.
3. Для нього збережено model artifact.
4. Параметри експерименту задокументовано, тож можна визначити конфігурацію моделі.

Порівняно з baseline `logreg-baseline`, accuracy зросла з 0.933 до 0.956, тобто на 0.023 (2.3 відсоткового пункту), а loss знизився з 0.191 до 0.141. Це позитивний результат, але тестова вибірка містить лише 45 прикладів. Тому різницю не слід автоматично трактувати як доказ стабільної переваги моделі: потрібні додаткові перевірки, наприклад повторні запуски або cross-validation.

Є також trade-off щодо складності: random forest із 100 деревами складніший за logistic regression. Для невеликого Iris-датасету різниця в точності може не виправдовувати складнішу модель у практичному продукті. Потрібно оцінити стабільність результатів, інтерпретованість і вимоги до обслуговування.

**Рішення: `Need more experiments` перед staging-рішенням.** `rf-depth3` є найкращим кандидатом за наданими результатами, але поки бракує повного audit trail, оцінки якості по класах і визначених критеріїв приймання. Після цих перевірок команда може ухвалити окреме рішення щодо staging. Production наразі не рекомендується.

## 4. Prometheus / Grafana та MLflow

### Prometheus показує

- Метрики `mlflow_accuracy` і `mlflow_loss` експортуються з MLflow.
- До метрик додано labels: `experiment`, `run_name`, `run_id`, `model_type`, що допомагає фільтрувати та зіставляти runs.
- У графіках є розрив приблизно о 08:34 UTC через перезапуск exporter-а. За вхідними даними, цей розрив не впливає на значення метрик.

### MLflow UI показує

- Таблицю п'яти runs з параметрами й метриками.
- Порівняльні графіки accuracy та loss.
- Деталі найкращого run `rf-depth3`.
- Наявність artifact у `rf-depth3` і відсутність artifacts у `rf-small` та інших runs.

### Разом ці інструменти допомагають

MLflow зберігає контекст експерименту: параметри, результати та artifact. Prometheus дає змогу спостерігати за експортованими метриками в часовому представленні й фільтрувати їх за labels. `run_id` є корисним для зв'язку між метрикою та конкретним запуском.

### Що ще потрібно перевірити

У текстових вхідних даних наведено значення метрик і опис графіків, але не самі числові точки з Prometheus. Тому фактичну відповідність кожного значення в Prometheus значенням MLflow неможливо незалежно підтвердити лише за цими даними. Команда має звірити `accuracy` та `loss` для кожного `run_id` в обох інструментах.

Ці метрики описують результати експериментів, а не обов'язково якість live predictions після deployment. Для production-моніторингу додатково потрібні метрики сервісу, latency/error rate, контроль вхідних даних і, коли стають доступними правильні labels, моніторинг якості прогнозів та data/model drift.

## 7. PM decision report

**Рекомендація: Need more experiments.**

`rf-depth3` є найкращим кандидатом серед п'яти runs за наданими метриками: його accuracy дорівнює 0.956, а loss — 0.141. Він також має збережений model artifact, на відміну від інших runs. Порівняно з baseline `logreg-baseline`, accuracy покращилась на 0.023, а loss зменшився на 0.050. Водночас тестова вибірка містить лише 45 прикладів, тому результат потребує перевірки стабільності. Для Iris-класифікації варто переглянути confusion matrix та precision/recall по кожному класу, оскільки лише accuracy не показує, які саме класи модель плутає. MLflow містить параметри й метрики runs, а Prometheus експортує `mlflow_accuracy` та `mlflow_loss` з labels, серед яких є `run_id`. Розрив у графіку близько 08:34 UTC пояснюється перезапуском exporter-а і, за наданою інформацією, не змінює значень метрик. Проте відповідність значень у MLflow і Prometheus ще потрібно звірити безпосередньо для кожного run. Перед staging потрібно зафіксувати run ID, версію коду й даних, погодити критерії приймання та перевірити відтворюваність. Потрібно також визначити owner рішення, rollback-план і моніторинг після deployment. До виконання цих кроків production deployment не рекомендується.

### Наступні дії

1. Отримати фактичний `run_id` для `rf-depth3` і додати його до звіту.
2. Звірити значення `mlflow_accuracy` і `mlflow_loss` у Prometheus з MLflow для всіх runs.
3. Провести cross-validation або повторні експерименти.
4. Переглянути confusion matrix, precision і recall по кожному класу.
5. Зберегти потрібні artifacts та зафіксувати версії коду, даних і залежностей.
6. Погодити staging acceptance criteria, відповідального за рішення, rollback та post-deployment monitoring.
